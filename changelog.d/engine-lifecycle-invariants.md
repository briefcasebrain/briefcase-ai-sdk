### Changed
- Engine lifecycle: the recorded current release is the one whose server runs. "Is release X running" is decided by the engine project's server container (its image id against X's record), not by a label a shared sidecar carries. An upgrade restarts and switches in one lock interval, treats any docker error as a failure that leaves the old release current, and keeps the installed TLS setting unless `--tls` or `--no-tls` is passed; an install next to a running release leaves that release current.
- `engine up` and an upgrade's restart start containers only when every volume they would mount is positively known to be this engine's or absent; an inspection that fails blocks. `engine uninstall` stops before deleting anything when docker cannot say what runs or `compose down` fails, and `--purge` deletes the secrets only after every engine volume is confirmed absent (docker missing or failing blocks; `--force-without-docker` is accepted only for an install that never created volumes).
- The running release is identified by all of its containers' image ids (and the Compose file when releases share every image); an engine that matches no install, a mix of releases, or two installs that fit are "unknown" and block an upgrade or uninstall with a message. A TLS change to the running version restarts it, `engine up` and installs decide under the same lock as an upgrade, and a client-only (`--no-images`) upgrade works without docker. The Docker context an install used is recorded, a purge refuses to probe a different daemon, and an ordinary uninstall that leaves volumes keeps a tombstone in `installed.json` so a later `engine uninstall --purge` can finish the job.
- Every destructive engine step (`uninstall`, `uninstall --purge`, `down --volumes`) runs in one order: lock, re-read state, verify the Docker daemon is the one the install used, ask for confirmation (`--yes`), and only then delete; `--dry-run` never deletes, and the deleting helpers cannot be called without a confirmation token. An unreadable `installed.json` or `engine.env` stops the command instead of being treated as empty (no replacement passwords, no "never had volumes"), a container that runs an unknown image in a recorded service is not taken for that release, and a client-only install of a version installed with images is refused.
- What an engine command deletes is decided in one function from `installed.json` read under the install lock: an install that lands while a purge waits is kept whole, `engine down` and `engine up` (whose `--remove-orphans` deletes containers) honour `--dry-run` before any compose call and a dry run takes no lock and creates nothing, a purge preview lists only what execution deletes, and every internal delete path needs the confirmation token. Volumes are removed only when the record says a stack ran and the Docker daemon is the one recorded for it (a client-only record never authorises it, whatever `--force-without-docker` says), and the calls are pinned to that daemon; stopping containers and removing images follow the same rule. The daemon is recorded before `engine up` or an upgrade's restart can create a volume, and they refuse where it cannot be identified. A truncated or partial `engine.env` (or a missing one while volumes may exist) stops an install or upgrade instead of being completed with new passwords, and a failed same-version TLS restart restores the Compose file as well as the record.
- `engine down` asks for confirmation like the other removals, and `engine up` no longer passes `--remove-orphans` (only an installed upgrade's restart does). A record from before `compose_used` existed counts as having run a stack when an install has one, so a purge verifies its daemon instead of deleting the secrets unchecked. Compose for `up` and an upgrade's restart, and every destructive call, runs against the verified daemon's endpoint (`DOCKER_HOST`), and the daemon is identified with Docker's own precedence (`DOCKER_CONTEXT`, then `DOCKER_HOST`). A TLS change is rolled back, record and Compose file, whenever the restart cannot start, not only when Compose fails. The `engine install --dry-run` hint no longer prints the install code.
- The Docker daemon is chosen the way the installed CLI chooses it (checked on Docker 29.8.2: `DOCKER_HOST` over `DOCKER_CONTEXT` over the active context), and everything after the check, the start guards included, runs against it: a context-selected daemon is pinned with `--context` (its TLS material stays), an environment-selected one by `DOCKER_HOST`. Plain `engine down` refuses a daemon the record does not name. `engine up` unsets `COMPOSE_REMOVE_ORPHANS` for its Compose calls and passes `--no-recreate`, so it never asks Compose to remove or recreate a container (moving to another release is an upgrade, which asks; a container that Compose removes because another Compose client created replicas during `up` on an empty stack is not detected). An ordinary uninstall writes the stack history before it drops the install, an error raised during an upgrade's restart rolls the transport back, the rollback never rewrites a record it cannot read, and `teardown` needs the confirmation token for container removal too.
