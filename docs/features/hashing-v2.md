# Cross-language hashing (RFC 8785)

Hash a JSON value in Python, TypeScript or Rust and get the same bytes and the same SHA-256,
floats included. It is the canonical form every new evidence feature (the chained store, audit
bundles) hashes with, and it is available to your own code.

Flow: **Verify**. Feature id: `hashing-v2`. Status: experimental.

The canonical form used so far (hash scheme `json-sorted-1`: sorted keys, Python's float
repr) disagrees between languages for floats: Python writes `1.0` and `1e+16`, JavaScript `1`
and `10000000000000000`. `jcs-1` is RFC 8785 (JSON Canonicalization Scheme): numbers are
written exactly as ECMAScript's `Number.prototype.toString` writes them, object keys are sorted
by UTF-16 code unit, strings are escaped as `JSON.stringify` escapes them, and the result is
UTF-8.

## The one command

```python
from briefcase.integrity import canonical_json_v2
canonical_json_v2({"score": 0.93})          # b'{"score":0.93}'
```

TypeScript: `canonicalJsonV2(value)` from `@briefcase-ai/runtime/integrity`. Rust:
`briefcase_core::integrity::canonical_json_v2(&value)`.

## What it writes or sends, and where

Nothing. It is a pure function. The golden vectors live in
`tests/vectors/canonical_json_v2.json` (generated by `tests/vectors/canonical_json_v2_vectors.py`
and asserted by the Python, TypeScript and Rust test suites, and by the `canonical-vectors` CI
job). They include the RFC 8785 Appendix B numbers and the section 3.2.3/3.2.4 examples with the
RFC's own expected output pinned, the published JCS test data
(github.com/cyberphone/json-canonicalization, `testdata/`, fetched 2026-11-22) pinned the same
way, floats, large integers, astral-plane keys, nested structures and escapes. While building
it, the Python and Rust number formatters were also compared with V8 (`String(x)` in Node.js
22.23.5) on 599,872 random doubles: no mismatch.

## Defaults and how to change them

| Where | Default | Opt in to `jcs-1` |
|---|---|---|
| `briefcase.integrity.canonical_json` | `json-sorted-1` (unchanged) | call `canonical_json_v2`, or `canonical_bytes(obj, "jcs-1")` |
| `HashChainAppender` (Python) | `json-sorted-1` | `HashChainAppender(store, hash_scheme="jcs-1")` |
| `HashChainAppender` (TypeScript) | `json-sorted-1` | `new HashChainAppender(store, { hashScheme: "jcs-1" })` |
| Chained store, audit bundles | `jcs-1` (only) | - |

Why the existing appenders keep `json-sorted-1`: they write into stores that older SDK releases
also read, and those verifiers do not know `hash_scheme`; they would reject `jcs-1` entries.
The chained store and bundles are new, so they start on `jcs-1`; nothing that already exists is
rehashed.

Every structure that carries a hash records the scheme that produced it: `hash_scheme` on
`HashChainEntry` (absent on old JSONL lines, which means `json-sorted-1`), on every chained-store
entry and checkpoint, and in bundle manifests. Verifiers dispatch on it, so a segment may mix
schemes and old data verifies forever. A `jcs-1` entry's hash input includes
`"hash_scheme": "jcs-1"`, so relabelling an entry from one scheme to the other changes its hash.

### Large integers

RFC 8785 numbers are IEEE-754 doubles. `jcs-1` accepts an integer when a double holds it
exactly (every integer up to 2^53 - 1, and larger ones such as 2^60) and writes it as that
double: 2^60 becomes `1152921504606847000`, as JavaScript writes it. Any other integer is
**rejected** (`ValueError` in Python, `RangeError` for a `bigint` in TypeScript,
`CanonicalError::InexactInteger` in Rust), never rounded. The rule depends only on the value, so
the three languages agree. Encode identifiers and exact decimals as strings.

To re-check stored canonical text, read it back with `parse_canonical_text` (Python, Rust) or
`JSON.parse` (TypeScript): they treat numbers beyond 2^53 as doubles, so `1152921504606847000`
re-encodes to the same bytes.

## How to turn it off or undo

Nothing to turn off: existing code keeps using `json-sorted-1` unless it opts in. Data written
with `jcs-1` stays verifiable by this and later releases; a release older than this one cannot
verify `jcs-1` entries.

## Limits and failure modes

- NaN, Infinity, lone surrogates (Python, TypeScript; Rust strings cannot hold them) and
  integers a double cannot hold are rejected.
- Unicode is not normalized (RFC 8785 section 3.1): `"Å"` and `"Å"` hash differently.
- Rust `serde_json` now has the `float_roundtrip` feature on in `briefcase-core`: without it,
  parsing could be one ULP off and stored floats would not re-hash identically.
- Not checked against a third-party JCS implementation at runtime; the pinned RFC and
  cyberphone outputs are the external reference.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `ValueError: jcs-1 cannot represent the integer ...` | Store that field as a string (`str(n)`), or keep `json-sorted-1` for that data. |
| Hash differs between Python and TypeScript | Check both used `jcs-1` (`canonical_json_v2` / `canonicalJsonV2`); `json-sorted-1` disagrees on floats by design. |
| Old chain entries fail after upgrading | They should not: entries without `hash_scheme` are `json-sorted-1`. Run `python -m pytest tests/integrity` and report the entry. |
| `vectors are out of date` in CI | Someone changed the canonical form. Only regenerate (`--write`) if that is intended; it changes every `jcs-1` hash. |
| Same text, different hash | Unicode normalization differs (NFC vs NFD); normalize before hashing if your inputs vary. |
